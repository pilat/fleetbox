# ADR: No Guest Agent — cloud-init NoCloud Is the Entire Provisioning Surface

**Date:** 2026-06-03
**Status:** Accepted

## Context

VM tools need some way to configure the guest (users, SSH keys, hostname) and often
want runtime communication with it (command execution, file copy, status). The common
solution is a guest agent: a binary injected into the guest that speaks a protocol with
the host (e.g. the QEMU guest agent, host-agent daemons, shared-folder provisioners).

Every guest agent creates: a versioning problem (agent and host must match), an
injection problem (how does the binary get inside?), a trust problem, and per-distro
compatibility work.

## Decision

1. **Zero fleetbox bytes inside the guest.** No agent, no helper binary, no host↔guest
   protocol. Because no protocol exists, none needs versioning.
2. **Provisioning happens exactly once, via cloud-init NoCloud seed ISO** (generated by
   `internal/seed` using `pilat/cloudiso`): one user, one SSH authorized key,
   passwordless sudo, hostname. Nothing else.
3. **After cloud-init has run, the guest is a plain distro reachable over SSH.** All
   further interaction is standard SSH/SCP — the same thing a human would do.

## Alternatives Considered

**Guest agent with a control protocol.** Rejected: versioning, injection, and
per-distro maintenance. This is where VM tooling complexity historically explodes.

**virtiofs mounts for host↔guest file exchange.** Deferred to v1: VZ-native virtiofs
(`--mount src:dst` + an fstab line via cloud-init) violates no principle (still nothing
of ours *running* in the guest), but `cp`/scp covers the v0 need. If added, mounts will
be explicit per-directory — never auto-mounting the whole home directory.

**Richer cloud-init payloads (package installs, arbitrary scripts).** Rejected:
fleetbox provisions access, not software. Software installation belongs to the test
that uses the VM — that's what SSH is for.

## Consequences

- The guest contract is "any distro whose cloud image runs cloud-init" — nothing more.
- No runtime guest introspection: fleetbox knows a VM is "ready" only by SSH
  reachability, not by an agent heartbeat. Boot-readiness detection is therefore
  polling-based (DHCP lease + TCP :22 + SSH auth).
- File transfer is scp-speed, not shared-folder-speed. Accepted for v0; the payload
  disk idea (go-ext4fs second disk) is the v1 answer for fast binary delivery.
